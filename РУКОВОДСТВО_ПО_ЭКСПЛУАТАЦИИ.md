## 1. Что это такое и для кого

### Простыми словами

Представьте, что ваша компания хочет получить сертификат SOC 2 — это международный стандарт безопасности, который проверяет: правильно ли вы храните данные клиентов, защищены ли ваши системы, соблюдаете ли вы правила доступа к информации.

Обычно подготовка к SOC 2 аудиту занимает 6–12 месяцев и требует найма специального аудитора за $50 000–$200 000. Большая часть работы — монотонный сбор доказательств: «покажите, что MFA включена», «покажите, что уволенные сотрудники деактивированы», «покажите журналы доступа».

**Sandbox Auditor** автоматизирует весь этот процесс:

- Сам подключается к AWS, GitHub, Okta, Jira и другим системам
- Сам собирает доказательства по всем 33 контролям SOC 2
- Сам оценивает: каждый контроль PASS (выполнен), FAIL (нарушен) или NEEDS_REVIEW (нужен человек)
- Сам создаёт Jira-тикеты на исправление найденных нарушений
- Сам генерирует черновики политик безопасности через AI
- Ведёт полную историю изменений — можно «перемотать» назад и посмотреть состояние на любую дату

### Для кого

| Роль | Что делает в системе |
|------|---------------------|
| **CISO / Head of Security** | Видит общую картину: какой процент контролей выполнен, какие риски критичны |
| **Compliance Officer** | Управляет политиками, аттестациями, следит за lifecycle документов |
| **DevOps / IT Admin** | Запускает сканеры, настраивает интеграции, читает технические отчёты |
| **Внешний аудитор** | Входит через Auditor Portal, смотрит доказательства, оставляет комментарии |
| **Сотрудник** | Проходит обучение по безопасности, подписывает политики |
| **Домохозяйка, случайно открывшая dashboard** | Видит большой процент (82%) и цветные статусы — зелёный/красный/жёлтый |

## 2. Что можно делать с этой системой

Это полный список функций системы. Ни одна не пропущена.

### 2.1 Автоматический сбор доказательств

- Сканирование AWS: S3 buckets (шифрование, публичный доступ), IAM пользователи (MFA, неактивные), EC2 (открытые порты, security groups), RDS (шифрование, публичный доступ), CloudTrail (логирование включено?)
- Сканирование GitHub: branch protection на main, secret scanning включён, PR review обязателен, прямые коммиты в main
- Сканирование Okta: уволенные сотрудники с активными аккаунтами, dormant-аккаунты (не заходили >90 дней), пользователи без MFA, SUPER_ADMIN роли
- 160 дополнительных проверок через Prowler (отраслевой инструмент безопасности)
- Сканирование уязвимостей с CVE-оценками и SLA по срокам устранения

### 2.2 Оценка соответствия

- Автоматическая оценка всех 33 контролей AICPA SOC 2 TSC 2017
- Детерминистический движок: FAIL-доказательство всегда даёт FAIL (не зависит от AI)
- Взвешенная оценка: критичные контроли (CC6.1 MFA) имеют больший вес
- Объяснение каждого FAIL: почему, какая цепочка зависимостей, какие риски затронуты
- Маппинг на другие фреймворки: ISO 27001, NIST CSF, CIS Controls

### 2.3 Управление политиками

- AI-генерация черновиков политик для 16 контролей (через Claude/Gemini)
- Полный lifecycle: черновик → на проверку → одобрен/отклонён → активен → истёк
- Версионирование: история всех версий каждой политики
- Разделение обязанностей (SoD): написал AI → проверяет человек → утверждает другой человек
- Push политик в GitHub репозиторий

### 2.4 Управление рисками

- Реестр рисков с оценкой likelihood × impact = risk score
- Автоматическое создание риска при FAIL-контроле
- Risk matrix — визуализация рисков по квадрантам
- Планы лечения рисков: mitigate / accept / transfer / avoid
- Связь рисков с контролями и активами

### 2.5 Remediation (исправление нарушений)

- Автоматическое создание Jira-тикетов при FAIL
- Idempotent создание: один и тот же FAIL не создаёт дублирующиеся тикеты
- Slack-кнопки для немедленных действий: отозвать IAM-доступ, применить patch — прямо из Slack
- Gap Analysis: AI-анализ что именно нужно сделать для перехода FAIL → PASS
- Отслеживание статуса remediation: открыт/в работе/закрыт

### 2.6 Управление людьми

- **Access Review**: регулярный обзор прав доступа, решения approve/revoke с аудит-следом
- **Security Training**: встроенная LMS с 5 курсами, сертификаты, отслеживание просроченных
- **Background Checks**: управление проверками сотрудников через Checkr API
- **HR Audit**: синхронизация с Okta, выявление уволенных с активным доступом
- **Опросы по знанию политик**: автоматические опросы с результатами

### 2.7 Управление вендорами

- Реестр вендоров с уровнями риска: critical / high / medium / low
- Автоматическая оценка риска вендора по заданным критериям
- Анкеты для вендоров (SIG Lite, CAIQ Lite форматы)
- Отслеживание DPA (Data Processing Agreement) — подписан ли
- Управление субпроцессорами (цепочка вендоров)
- DocuSign-интеграция для подписания договоров

### 2.8 Pentest Management

- Загрузка отчётов о пентестах
- Трекинг findings (уязвимостей из пентеста) с SLA по устранению
- Статусы: open / in_progress / fixed / accepted_risk
- История пентестов по годам

### 2.9 Аудиторский портал

- Отдельный защищённый вход для внешних аудиторов
- Просмотр доказательств с фильтрацией по контролю
- Оставление комментариев к контролям
- Сводка готовности к аудиту (audit readiness summary)

### 2.10 Trust Center

- Публичная страница (без логина) для клиентов и партнёров
- Показывает общий % соответствия, активные сертификации
- NDA-gate: полные детали только после подписания NDA
- Запрос доступа к полному отчёту через форму

### 2.11 Compliance as Code

- YAML-декларации контролей с автоматическими проверками
- Запуск CaC-контролей: каждый контроль — это код с чёткими условиями PASS/FAIL
- Approval workflow: авто-исправимые контроли vs требующие человека
- SLA на исправление в спецификации

### 2.12 Time Machine

- Посмотреть состояние compliance на любую дату в прошлом
- «Машина времени»: как выглядел Dashboard 3 месяца назад?
- Сравнение двух моментов: что изменилось за последний квартал?
- Поиск регрессий: когда именно контроль перешёл из PASS в FAIL?

### 2.13 Event Sourcing и Audit Trail

- Полная история всех изменений в системе (append-only, нельзя удалить)
- Цепочка причинности: почему изменился контроль → какое событие это вызвало
- Replay: детерминистически воспроизвести любой момент истории
- Compliance Timeline: график % соответствия за любой период с любой детализацией

### 2.14 Compliance Graph

- Граф зависимостей: CC6.1 зависит от CC6.3 зависит от CC1.1
- Распространение риска: FAIL одного контроля влияет на смежные
- Визуализация: какие контроли связаны с данным вендором
- Поиск кратчайшего пути между двумя контролями
- Найти все контроли, затронутые конкретным риском

### 2.15 Asset Management

- Реестр IT-активов: устройства, облачные аккаунты, репозитории, базы данных, сотрудники
- Привязка контролей к активам: «CC6.1 применяется к этим 47 устройствам»
- Синхронизация из MDM систем (Jamf Pro, Microsoft Intune)
- Синхронизация из сканера (автоматическое обнаружение)
- Compliance posture по активу: какие контроли выполнены для этого устройства

### 2.16 Governance

- Граф полномочий: кто может одобрять что
- Аттестации с криптографической подписью (HMAC-SHA256)
- TTL на аттестации: истекает через X часов
- Отзыв аттестаций с аудит-следом
- Проверка покрытия аттестациями всех контролей

### 2.17 Chaos Engineering

- Намеренный ввод нарушений для проверки системы реакции
- Инъекция: отключить MFA, открыть порт, отозвать branch protection
- Измерение SLA реакции: через сколько минут система обнаружила нарушение?
- Восстановление исходного состояния одной кнопкой

### 2.18 Отчётность

- HTML-отчёт: красивый, с таблицами, grafana-скриншотами, подходит для отправки
- PDF-отчёт: для официального предоставления аудитору
- История отчётов: все когда-либо сгенерированные отчёты сохраняются
- Экспорт на любую дату

### 2.19 Мониторинг

- Prometheus-метрики: количество запросов, latency, ошибки
- Grafana-дашборд: 9 панелей с реальными метриками
- Rate limiting: защита от перегрузки API (10 запросов/мин на login)
- Security headers на всех ответах

### 2.20 Webhooks и Real-time

- Получение событий от GitHub (push, PR, secret alert)
- Получение событий от Okta (пользователь деактивирован, роль изменена)
- Получение команд от Slack (кнопки подтверждения/отзыва доступа)
- Celery: тяжёлые задачи (полный аудит) выполняются в фоне, не блокируя UI

### Docker-сервисы

```
docker compose up -d → 6 сервисов

  grafana      :3000   дашборды (логин: admin / soc2admin)
```

### Слои архитектуры

| Слой | Что делает | Ключевые файлы |
|------|-----------|----------------|
| **Presentation** | HTML страницы, API эндпоинты | `ui/index.html`, `*_routes.py` |
| **Application** | Бизнес-логика, оркестрация агентов | `ui_server.py`, `orchestrator.py` |
| **Domain** | Compliance-логика, правила, онтология | `compliance_engine.py`, `compliance_ontology.py`, `control_mapping.py` |
| **State** | Единый источник истины о состоянии | `compliance_state_engine.py`, `compliance_graph.py` |
| **Events** | Все изменения как события | `event_bus.py`, `event_sourcing.py` |
| **Infrastructure** | DB, HTTP-клиенты, внешние API | `database.py`, `db_repository.py`, `*_client.py` |
| **AI Advisory** | Советы AI (не принимают решений) | `ai_advisor.py`, `ai_decision_log.py` |

### Принципы которые нельзя нарушать

1. **AI не принимает решений** — только советует. Deterministic engine (`compliance_engine.py`) всегда главный.
2. **Audit log неизменяем** — записи в `AuditEvent` и `EventStore` никогда не удаляются.
3. **Аттестации подписаны криптографически** — их нельзя подделать без знания `SECRET_KEY`.
4. **SoD** — тот, кто написал политику, не может её сам одобрить.

## 4. Модули — подробное описание каждого

### 4.1 Ядро системы

#### `ui_server.py` — Главное приложение
Сердце системы. FastAPI-сервер который:
- Отдаёт HTML-страницы браузеру
- Предоставляет REST API для всех операций
- Управляет авторизацией через JWT-токены в Cookie
- Запускает агентов через SSE (Server-Sent Events) — результаты приходят в реальном времени
- Scheduled job: полный аудит каждый день в 03:00 UTC
- Prometheus-метрики на `/metrics`
- Rate limiting: 10 запросов в минуту на `/api/auth/login`

#### `auth.py` — Авторизация
JWT-токены хранятся в HTTP-only Cookie (защита от XSS). Роли:
- `admin` — полный доступ ко всему
- `auditor` — read-only + комментарии
- `reviewer` — может одобрять политики и access reviews
- `scanner` — может только запускать сканирование

Учётные записи по умолчанию (меняйте в `.env`!):
```
admin@example.com / admin123
auditor@example.com / auditor123
```

#### `config.py` — Конфигурация
Единое место для всех настроек. Читает из `.env` файла или переменных окружения. Pydantic автоматически валидирует типы и наличие обязательных значений.

#### `database.py` — База данных
Поддерживает два режима:
- **Dev**: SQLite (`compliance.db` в папке проекта) — без установки чего-либо
- **Prod**: PostgreSQL — задать `DATABASE_URL=postgresql+asyncpg://...`

При отсутствии `DATABASE_URL` система работает через JSON-файлы в папке `data/`.

---

### 4.2 Агенты сбора доказательств

#### `scanner.py` — AWS Scanner
Подключается к AWS (или LocalStack в dev-режиме) и проверяет:

| Проверка | SOC 2 контроль | Что ищет |
|---------|---------------|---------|
| S3 Public Access | CC6.1 | Bucket публично доступен? |
| S3 Encryption | CC6.7 | Шифрование включено? |
| IAM MFA | CC6.1 | MFA у всех пользователей? |
| IAM Inactive Users | CC6.2 | Аккаунты > 90 дней без входа |
| EC2 Security Groups | CC6.6 | Открытые порты SSH/RDP/DB |
| RDS Encryption | CC6.7 | БД зашифрована? |
| CloudTrail | CC7.2 | Логирование включено? |

Результат: файл `controls_map.json` с обновлёнными статусами.

#### `prowler_runner.py` — Prowler Runner
Prowler — популярный open-source инструмент для 160+ проверок безопасности AWS. Запускается локально (требует `pip install prowler`). Не работает внутри Docker (это норма для dev-режима).

Запуск:
```bash
python3 prowler_runner.py
```

#### `github_agent.py` — GitHub Agent
Проверяет репозиторий на:
- Branch protection на `main` — PR обязателен?
- Secret scanning включён?
- Dependabot alerts активен?
- Прямые коммиты в `main` за последние 30 дней
- Открытые security issues

#### `hr_agent.py` — HR Agent
Синхронизируется с Okta и проверяет:
- Уволенные сотрудники (из HR roster) с активными Okta аккаунтами
- Сотрудники без пройденного обязательного обучения
- Аккаунты без MFA
- Пользователи с привилегированными ролями без обоснования

#### `mdm_agent.py` — MDM Agent
Инвентаризация устройств через Jamf Pro или Microsoft Intune:
- Список всех управляемых устройств
- Включён ли FileVault (шифрование диска)?
- Установлен ли EDR (endpoint security)?
- Актуальна ли ОС?

#### `vendor_risk_agent.py` — Vendor Risk Agent
Оценивает каждого вендора по критериям риска:
- Доступ к данным клиентов?
- Подписан ли DPA?
- Есть ли собственные сертификаты (SOC 2, ISO 27001)?
- Дата последней проверки

#### `gap_analysis_agent.py` — Gap Analysis Agent
AI-анализ: для каждого FAIL-контроля объясняет что именно нужно сделать для перехода в PASS. Использует AI только для генерации рекомендаций — сам статус AI не меняет.

### 4.3 Compliance-движок (ядро логики)

#### `compliance_engine.py` — Deterministic Engine
**Главный арбитр.** Никогда не использует AI. Правила:
1. Есть хотя бы одно FAIL-доказательство → контроль FAIL
2. Все обязательные доказательства присутствуют и свежие → PASS
3. Иначе → NEEDS_REVIEW (нужен человек)

Уверенность (confidence): 0.0 → 1.0. При FAIL с критичным доказательством = 1.0 (абсолютная уверенность).

#### `compliance_state_engine.py` — State Engine (P4)
Единый источник истины о текущем состоянии всего compliance. Хранит кэш всех контролей. Умеет объяснить:
- Почему контроль FAIL → dependency chain → какие риски затронуты → когда SLA истекает
- Какой была история изменений
- Сколько всего Evidence, по категориям

#### `compliance_graph.py` — Compliance Graph (P2)
Граф зависимостей между всеми сущностями системы:
```
CC6.1 (MFA) ──зависит──► CC1.1 (Personnel Security)
     │
     └──риск──► RISK-003 (Unauthorized Access)
                    │
                    └──влияет──► Vendor: AWS
```

BFS-обход для поиска всех затронутых контролей при изменении одного.

#### `compliance_ontology.py` — Ontology (P8)
Machine-readable описание каждого из 33 контролей в YAML. Для каждого контроля:
- Какие доказательства нужны
- Зависимости от других контролей
- Вес риска (1–5)
- SLA на исправление (в часах)
- Маппинг на ISO 27001, NIST, CIS
- Можно ли исправить автоматически
- Кто владелец (роль)

#### `event_bus.py` — Event Bus (P3)
Внутренняя шина событий. Когда что-то меняется → публикуется событие → подписчики реагируют:

| Событие | Кто публикует | Кто слушает |
|---------|--------------|-------------|
| `EVIDENCE_ADDED` | evidence_client | SLA checker, AuditTrail |
| `CONTROL_STATUS_CHANGED` | compliance_engine | Risk escalation, Slack |
| `RISK_ESCALATED` | risk module | Slack (critical only) |
| `POLICY_APPROVED` | policy_lifecycle | AuditTrail, governance |
| `SLA_BREACH` | event_bus внутри | AIDecisionLogger |

#### `event_sourcing.py` — Event Store (P9)
Append-only хранилище всех событий. Каждое событие имеет:
- `sequence_number` — монотонно возрастающий номер
- `causation_id` — какое событие вызвало это
- `correlation_id` — группировка событий одной транзакции

Позволяет детерминистически воспроизвести любой момент истории.

---

### 4.4 AI-слой (только advisory)

#### `ai_advisor.py` — AI Advisor
Генерирует рекомендации по контролям и remediation. **Важно:** любой ответ AI содержит:
```
is_advisory_only = True
disclaimer = "AI suggestion — requires human review"
```
AI не может изменить статус контроля напрямую.

#### `ai_decision_log.py` — AI Decision Log
Каждое обращение к AI записывается:
- Что спросили
- Что AI ответил
- Уверенность AI (0–1)
- Кто запросил
- Было ли предложение принято человеком

Это explainability layer — аудитор может проверить каждое AI-решение.

#### `policy_agent.py` — Policy Generator
Генерирует черновики политик безопасности через LLM (Claude или Gemini через OpenRouter). Поддерживает 16 типов политик: Access Control, Change Management, Incident Response и т.д. После генерации черновик обязательно проходит human review.

---

### 4.5 Persistence (хранение данных)

#### `models.py` — ORM модели
SQLAlchemy-модели для всех основных сущностей. Все поля с типами — нет "magic strings".

#### `db_repository.py` — Repository Pattern
Каждая сущность имеет свой репозиторий с методами `get`, `create`, `update`, `delete`. Бизнес-логика не знает о деталях хранения.

#### `event_store` (часть `event_sourcing.py`)
Отдельное хранилище событий. В dev-режиме: `data/event_store.json`. Атомарная запись через `os.replace()` + `fcntl.flock`. Нельзя удалить запись — только добавить.

### 4.6 Governance

#### `governance_graph.py` — Governance Graph (P6)
Формализует кто что может одобрять:
- `ciso` — может одобрять политики и принимать риски
- `compliance_officer` — может аттестовать контроли
- `manager` — может одобрять access reviews
- Делегирование: manager → compliance_officer

Аттестации подписаны HMAC-SHA256 с `SECRET_KEY` — их нельзя подделать. TTL: истекают через N часов.

### Честный вывод

**Где Sandbox Auditor превосходит Vanta:**
- Глубина архитектуры (event sourcing, compliance graph, state engine)
- Прозрачность AI-решений (все действия AI записаны, explainable)
- Time Machine — уникальная функция для ретроспективных аудитов
- Chaos Engineering — нет аналогов на рынке
- Стоимость: $0 против $7 000–50 000/год
- Полный контроль над данными (self-hosted)

**Где Vanta превосходит Sandbox Auditor:**
- 200+ готовых интеграций (Sandbox: ~14)
- Multi-tenant (несколько организаций)
- GCP и Azure сканеры
- Native HIPAA, GDPR, PCI DSS
- Managed SaaS (не нужно администрировать)
- Enterprise customer support

**Для кого Sandbox Auditor:**
- Стартапы с техкомандой, которым нужен SOC 2 без $50K/год
- Компании в regulated industries (финтех, healthtech), где важна explainability AI
- Команды, которым нужна максимальная гибкость и кастомизация
- R&D и исследовательские проекты

## 15. Устранение неполадок

### Сервер не запускается

```bash
# Проверить порт занят
lsof -i :8080

# Проверить импорты
python3 -c "import ui_server"

# Проверить конфиг
python3 -c "from config import get_settings; print(get_settings())"
```

### Агент "завис" в статусе Running

Система имеет watchdog-таймер: через 5 минут зависший агент автоматически останавливается. Если этого не произошло:

```bash
# Проверить запущенные агенты
curl -b "access_token=TOKEN" http://localhost:8080/api/running

# Перезапустить сервер (убивает все агенты)
pkill -f ui_server.py
python3 ui_server.py
```

### Prowler не работает в Docker

Prowler должен запускаться локально (не в контейнере):
```bash
# Установить Prowler
pip install prowler

# Запустить напрямую
python3 prowler_runner.py
```

### База данных: ошибка "metadata is reserved"

Если встречается в старых версиях кода — это известная проблема SQLAlchemy. Исправлено: `metadata` переименован в `extra_data` с column alias.

### Тесты падают: "asyncio mode not set"

```bash
# Убедиться что pytest.ini содержит:
cat pytest.ini
# asyncio_mode = auto
```

### LocalStack: ошибки подключения

```bash
# Проверить что LocalStack запущен
docker compose ps localstack

# Перезапустить
docker compose restart localstack

# Проверить доступность
curl http://localhost:4566/_localstack/health
```

### Grafana: нет данных на дашборде

```bash
# Убедиться что Prometheus скрейпит метрики
curl http://localhost:9090/targets

# Сгенерировать трафик
curl http://localhost:8080/health
curl http://localhost:8080/api/controls
```

### Логи

```bash
# Логи всех Docker-сервисов
docker compose logs -f

# Только ui_server
docker compose logs -f ui_server

# Структурированные JSON-логи
docker compose logs ui_server | python3 -m json.tool
```

## 16. Глоссарий

| Термин | Объяснение |
|--------|-----------|
| **SOC 2** | Service Organization Control 2 — стандарт безопасности для SaaS-компаний. Проверяет: безопасность, доступность, конфиденциальность данных |
| **AICPA** | American Institute of Certified Public Accountants — орган, выпустивший стандарт SOC 2 |
| **TSC 2017** | Trust Services Criteria 2017 — конкретный набор из 33 контролей SOC 2 |
| **Control** | Контроль — конкретное требование безопасности. Например: CC6.1 = MFA обязательна |
| **Evidence** | Доказательство — данные подтверждающие что контроль выполняется. Например: список IAM пользователей с включённой MFA |
| **PASS / FAIL / NEEDS_REVIEW** | Статусы контроля: выполнен / нарушен / требует ручной проверки |
| **CISO** | Chief Information Security Officer — директор по информационной безопасности |
| **Compliance Officer** | Специалист по соответствию требованиям |
| **SoD** | Segregation of Duties — разделение обязанностей. Нельзя одному человеку создать и одобрить одно решение |
| **SLA** | Service Level Agreement — допустимый срок. В контексте: через сколько часов FAIL должен быть исправлен |
| **DPA** | Data Processing Agreement — соглашение об обработке данных (GDPR) |
| **MDM** | Mobile Device Management — система управления устройствами (Jamf Pro, Intune) |
| **HMAC** | Hash-based Message Authentication Code — криптографическая подпись для верификации данных |
| **Event Sourcing** | Паттерн хранения данных: все изменения хранятся как последовательность событий, а не только текущее состояние |
| **Deterministic** | Детерминистический — одинаковые входные данные всегда дают одинаковый результат (в отличие от AI) |
| **BFS** | Breadth-First Search — обход графа в ширину. Используется для поиска затронутых контролей |
| **Replay** | Воспроизведение истории событий для восстановления состояния системы на определённый момент |
| **Attestation** | Аттестация — официальное подтверждение человеком что контроль выполнен, с криптографической подписью |
| **Chaos Engineering** | Намеренное введение сбоев для проверки устойчивости системы реагирования |
| **Confidence Score** | Уверенность — число от 0 до 1 показывающее насколько надёжно доказательство |
| **Gap Analysis** | Анализ пробелов — что конкретно нужно сделать чтобы закрыть нарушения |
| **CVE** | Common Vulnerabilities and Exposures — база данных известных уязвимостей |
| **CVSS** | Common Vulnerability Scoring System — система оценки серьёзности уязвимостей (0–10) |
| **Prowler** | Open-source инструмент для AWS security checks (160+ проверок) |
| **LocalStack** | Локальный эмулятор AWS для разработки и тестирования |
| **Celery** | Система очередей задач для Python (асинхронный запуск долгих операций) |
| **Event Bus** | Внутренняя шина событий — механизм pub/sub для обмена сообщениями между модулями |
| **Trust Center** | Публичная страница с информацией о безопасности компании для клиентов |
| **Audit Trail** | Audit trail — полная хронологическая история всех действий в системе |
